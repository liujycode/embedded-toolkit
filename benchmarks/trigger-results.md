## 判定方法（为什么不能靠文本匹配）

技能名会出现在系统提示的技能清单里（Claude Code 的 `slash_commands`、OpenCode 的技能列表），任何“技能名出现即触发”的文本匹配会把全部用例误判为触发（已实测确认）。本记录只认结构化信号：

- **Claude Code**：`Launching skill: <技能>` 事件、`commandName` 成功回执；另加“带技能安装路径（`skills/<技能>/scripts/...`）的脚本调用”作为执行级证据（技能文档里的示例命令不算）。
- **OpenCode**：`tool="skill"` 且 `name=<技能>` 的加载事件；`tool="bash"` 且命令含脚本调用。

解析容错：BOM、字符串内终端转义字符、破损行（原始行兜底需同时出现工具类型与名称/脚本）。

复现命令：

```
python tools/trigger_run.py --agent claude|opencode --skill <技能名> --out <目录>
python tools/trigger_eval.py --dir <目录> --agent claude|opencode --skill <技能名> \
    --script verify.py --subcommands check,rules     # 核验器；百事通用 --script lookup.py
```

### v1.10.0 用例措辞修订与复测（核验器，p06/p09/p22）

第三轮里核验器的 3 个漏报（p06 DMA 顺序、p09 HSIRDY、p22 字段名拼写）共性同为“模型凭知识直接作答”。

| 用例 | 修订要点 | Claude Code | OpenCode |
|---|---|---|---|
| p06 DMA 顺序 | “帮我核验这段 DMA 配置有没有错” | ✅ | ✅ |
| p09 HSIRDY | “帮我对照 SVD 核验这段 RCC 时钟使能代码” | ✅ | ✅ |
| p22 字段名拼写 | “帮我核验一下” | ✅ | ❌（见下） |

- 复测结果：**Claude Code 3/3、OpenCode 2/3**。

   留在目录里，后续 n06/n09 扫到文件导致假阳性。运行器改为**每例新建目录、跑完即清**
   （`--keep` 可保留用于取证）；修复后核验器反例 20/20 全干净。
2. **核验类正例自带代码片段（v1.2.0 用例修订）**：无附件的“这段代码”式探针在 13 例子集实测
   claude 2/9、opencode 7/9（模型先要代码 / 探索文件系统，不加载技能）；真实用法是代码在
   上下文里，故修订为自带片段，修订后 claude 19/22、opencode 21/22。
3. 无头单次会话、自动批准工具，与交互式使用存在行为差异。
4. Claude Code 侧模型经 CC Switch 代理（deepseek-v4-flash），非 Anthropic 原版模型；代理会丢部分事件块。
5. 判定只看“技能是否被加载 / 脚本是否被调用”，不评价答案质量——p06/p09 这类漏报的答案本身正确，
   但没有走“对照 SVD 核验”的证据链。
6. 每例仅运行一次（首跑）；漏报额外复跑 1 次用于区分抖动与系统性，已单列，不计入首跑准确率。
7. 会话会自行探索文件系统（本机有真实工程），个体时长波动大（6s–455s）；超时用例放宽后重跑。
8. 已知路由边界：单属性提问（“字段宏存不存在”“地址是什么”）在 v1.2.0 版用例下会被百事通
   的 `macros`/`addr` 截走；改为整段核验措辞后稳定路由到核验器。
