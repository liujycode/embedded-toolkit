# 决策树全量参考（自动生成）

## hardfault — 代码跑飞 / HardFault

高频根因（按实战经验排序，非实测统计）：

1. 中断服务函数里调用非重入/阻塞函数（printf/malloc/延时）
2. 栈溢出（局部大数组/递归/RTOS 任务栈给小了）
3. 外设时钟未开就访问寄存器（RCC 使能遗漏）
4. DMA 缓冲区被编译器优化/放错内存段（DTCM 里 DMA 到不了）
5. 中断优先级超过 BASEPRI 屏蔽线却调用了 FreeRTOS API（FromISR 后缀没加）

- **get-frame** 取 fault 栈帧
  - 症状：HardFault 已触发，先定位现场
  - 证据动作：判断用 PSP 还是 MSP（EXC_RETURN bit2），取 PC/LR；有 RTOS 先分清是哪个任务的栈
  - 判定：拿到出错 PC 后进入 CFSR 解读分支
  - 依据：ARMv7-M Architecture Reference Manual (DDI 0403)
  - 转入：boot/vtor
  - **iaccvio** 非法地址访问（IACCVIOL/MUNSTALL）
    - 症状：CFSR.IACCVIOL 或 MemManage 置位
    - 证据动作：查 PC 指向：0xE0000000 段=函数指针未初始化；随机地址=野指针
    - 判定：野指针/函数指针问题
    - 对策：dump 调用栈，找最近的数组/指针操作
    - 对策：检查函数指针表初始化顺序
    - 依据：ARMv7-M Architecture Reference Manual (DDI 0403)
  - **precise** 精确总线错误（PRECISERR）
    - 症状：CFSR.PRECISERR 置位，出错指令可直接定位
    - 证据动作：查该指令访问的地址——通常是外设没开时钟就访问
    - 判定：RCC 使能遗漏（最高频）或地址越界
    - 对策：核对 RCC->AHB1ENR/APB1ENR/APB2ENR 对应位
    - 对策：用 embedded-register-verify check 复查全部寄存器写入
    - 依据：ARMv7-M Architecture Reference Manual (DDI 0403)
  - **imprecise** 非精确总线错误（IMPRECISERR）
    - 症状：CFSR.IMPRECISERR 置位，写缓冲延迟导致 PC 不准
    - 证据动作：开启 write-through 或查 DMA 目标地址合法性
    - 判定：DMA 目标地址错误或写缓冲时序
    - 对策：核对 DMA 的 M0AR/M1AR 目标地址
    - 对策：暂时关写缓冲（SCnB 位）复现定位
    - 依据：ARMv7-M Architecture Reference Manual (DDI 0403)
    - 转入：dma/corrupt
  - **undefinstr** 未定义指令（UNDEFINSTR）
    - 症状：CFSR.UNDEFINSTR 置位
    - 证据动作：查函数指针是否跳到数据区；查中断向量表位置与编译优化
    - 判定：函数指针/向量表错位
    - 对策：核对 VTOR 偏移（Bootloader 跳 App 必查）
    - 对策：检查链接脚本的向量表段
    - 依据：ARMv7-M Architecture Reference Manual (DDI 0403)
  - **stkerr** 栈溢出（STKERR/MSTKERR）
    - 症状：CFSR.STKERR 或 MSTKERR 置位
    - 证据动作：填充栈为 0xA5 查水位；RTOS 用 uxTaskGetStackHighWaterMark
    - 判定：栈溢出（高频！）
    - 对策：加大任务栈/去局部大数组
    - 对策：开 FreeRTOS 的 configCHECK_FOR_STACK_OVERFLOW=2
    - 依据：FreeRTOS 官方文档（uxTaskGetStackHighWaterMark / 栈溢出检查）
- **snapshot** 复现策略
  - 症状：故障偶发难抓
  - 证据动作：加故障快照：fault 时把 CFSR/HFSR/栈帧 dump 到保留 RAM 或串口，复位后打印
  - 判定：拿到偶发故障的现场证据
- **nocep-fpu** UsageFault：NOCP（FPU 没使能就执行浮点指令）
  - 症状：CFSR 的 NOCP 置位；一跑浮点运算或进入浮点中断就 fault
  - 证据动作：读 CFSR 确认 NOCP；读 SCB->CPACR 看 CP10/CP11 是否使能；查工程的 FPU 选项（__FPU_PRESENT/__FPU_USED）
  - 判定：FPU 未使能或编译选项与硬件不匹配
  - 对策：SystemInit 里使能 CP10/CP11（或开编译器的硬件浮点选项让启动文件代做）
  - 对策：FreeRTOS 注意浮点上下文保存与懒压栈配置
  - 依据：CMSIS Core (SCB->CPACR/FPU 使能)；ARMv7-M Architecture Reference Manual (DDI 0403)
  - 转入：rtos/nvic-map
- **lockup** LOCKUP 状态（fault 处理器里又 fault）
  - 症状：整机无响应且复位才恢复；调试器连上看到内核处于 LOCKUP
  - 证据动作：查 HFSR（FORCED/VECTTBL）；配合故障快照看第一现场——是不是在 NMI/HardFault 处理器里又触发了 fault
  - 判定：双重故障进入 LOCKUP
  - 对策：fault 处理器里只做最安全的记录动作（别再碰外设、别再嵌套）
  - 对策：先解决被 FORCED 升级成 HardFault 的原始 fault
  - 依据：ARMv7-M Architecture Reference Manual (DDI 0403)
  - 转入：boot/reset-source

## comm — 通信链路不通（I2C/SPI/UART）

高频根因（按实战经验排序，非实测统计）：

1. GPIO 复用模式没配对（AF/开漏/上拉）
2. 外设或 GPIO 时钟未使能
3. SPI 的 CPOL/CPHA 与从机手册不符
4. 波特率/分频计算错误（误差>2%）
5. DMA 缓冲区不可达或 NDTR/标志位处理顺序错
6. 跨设备互联的物理层问题（共地缺失/TX-RX 接反/电平不匹配，跨板串口或 485 时先查）

- **layer1-config** 第一层：配置对不对（不用仪器）
  - 症状：链路完全无响应/初始化后外设不工作
  - 证据动作：读回寄存器验证：RCC 使能位、GPIO MODER/AFR、波特率 BRR
  - 判定：回读值与预期不符=配置问题，本层解决
  - 对策：跨板/跨模块先查物理层：共地、TXD/RXD 方向、电平匹配（TTL/RS232/RS485），再进配置层
  - 对策：按'时钟→GPIO→外设→中断→使能'顺序逐项回读
  - 对策：用 embedded-register-verify check 复查初始化代码
  - 转入：boot/clock-stuck
- **layer2-timing** 第二层：时序对不对（要仪器）
  - 症状：配置回读全对但通信仍失败
  - 证据动作：示波器/逻辑分析仪抓波形：I2C 看 ACK 卡在哪个字节；SPI 比对第一字节位序；UART 看波特率误差
  - 判定：波形与协议不符=时序问题
  - 对策：I2C：SDA 拉死→9 脉冲解救或复位外设电源
  - 对策：SPI：CPOL/CPHA 先读从机手册时序图，四组合试错不如读手册
  - 对策：UART：波特率误差<2%，HSI±1% 精度不够就换 HSE
  - 转入：pwr/stop-clock
- **layer3-dataflow** 第三层：数据流对不对
  - 症状：物理层通了但数据不对
  - 证据动作：查 DMA 配置（内存段/宽度/循环）、中断标志清除顺序、IDLE+DMA 不定长方案
  - 判定：数据流配置问题
  - 对策：I2C F1 系：先读 SR 再读 DR 的顺序陷阱
  - 对策：UART 空闲中断：先清 IDLE 再使能，用 NDTR 算长度
  - 对策：缓冲区放 DMA 可达内存段（H7 的 DTCM 到不了）
  - 转入：dma/not-start
- **half-duplex** 半双工链路（RS485 等）方向切换
  - 症状：对端收得到我发的，我收不到回包；或报文最后一字节丢
  - 证据动作：查 DE/RE 方向脚的切换时机与极性：是否等发送完成就切回接收
  - 判定：方向控制时机/极性问题
  - 对策：发送完等 TC（发送完成）标志再拉方向脚——TXE 只表示数据寄存器空，最后一个字节还在移位
  - 对策：或用 USART 自带的 RS485 方向控制（CR3 的 DEM/DEAT/DET）
  - 转入：can/can-phy

## dma — DMA 异常（丢数据/错位/不启动）

高频根因（按实战经验排序，非实测统计）：

1. 非循环模式跑完即停（没有重启/改 circular）
2. Cache 一致性未处理（H7/F7）或缓冲区在 DMA 不可达内存段
3. PSIZE/MSIZE 与外设寄存器宽度不匹配
4. 缓冲区被主程序与 DMA 同时读写（无 ping-pong）
5. 请求源使能没开（如 USART 的 DMAR 位）

- **once-only** 只收到第一次
  - 症状：DMA 只传一轮，之后无数据
  - 证据动作：查模式位：非循环跑完即停；查接收缓冲/NDTR 是否重装
  - 判定：模式/重启问题
  - 对策：改 circular 模式
  - 对策：每次传输前重启 DMA 并重装计数
- **misaligned** 数据错位/宽度错
  - 症状：数据错位、半字当字节
  - 证据动作：查 PSIZE/MSIZE 与外设寄存器宽度匹配；查 DMA 请求映射表确认通道
  - 判定：宽度/通道映射问题
  - 对策：PSIZE=MSIZE=外设数据宽度
  - 对策：按参考手册的 DMA 请求映射表核对通道
  - 转入：hardfault/precise
- **corrupt** 数据偶发损坏
  - 症状：大多数正确，偶发帧坏
  - 证据动作：查主程序与 DMA 是否同时读写缓冲（无 ping-pong/双缓冲）；中断处理是否太慢被覆盖
  - 判定：并发/时效问题
  - 对策：做 ping-pong 双缓冲
  - 对策：缩短 ISR 或用半满/全满双中断
  - 转入：hardfault/imprecise
- **cache** Cache 一致性（H7/F7）
  - 症状：DMA 收到的数据是旧数据/主核读到旧数据
  - 证据动作：检查 D-Cache 使能状态；对缓冲区做 Invalidate/Clean；确认 32 字节对齐
  - 判定：Cache 一致性问题
  - 对策：收方向：SCB_InvalidateDCache_by_Addr
  - 对策：发方向：SCB_CleanDCache_by_Addr
  - 对策：或把缓冲放非 Cache 区并 32 字节对齐
  - 依据：STM32 参考手册（如 RM0433，Cache 一致性）
- **not-start** DMA 根本没启动
  - 症状：配置全做了但没有传输
  - 证据动作：查外设侧 DMA 请求使能（USART 的 DMAR/DMAT 位）+ DMA 控制器时钟
  - 判定：请求链没打通
  - 对策：开外设的 DMA 使能位
  - 对策：回读 DMA_CR 确认 EN 位已置
  - 转入：comm/layer3-dataflow
- **dmamux** DMAMUX 请求映射错（G4/H7/L4+ 等新系列）
  - 症状：DMA 触发不了，或被不相干的请求误触发
  - 证据动作：查 DMAMUX 通道的 DMAREQ_ID 选择；查是否多个通道映射到同一请求线
  - 判定：请求映射/复用问题
  - 对策：按参考手册的 DMAMUX 请求表核对 DMAREQ_ID
  - 对策：确认 MUX 通道与 DMA 通道的对应关系（不是每片都一样）
  - 依据：STM32 参考手册（如 RM0440，DMA 章节）

## rtos — RTOS 应用异常

高频根因（按实战经验排序，非实测统计）：

1. 任务栈太小导致溢出踩 TCB
2. 任务无阻塞点饿死低优先级（看门狗复位是典型症状）
3. 中断里调用非 FromISR API
4. 中断优先级数值与 configMAX_SYSCALL_INTERRUPT_PRIORITY 关系搞反
5. 用二值信号量做资源保护导致优先级反转

- **task-not-run** 任务不跑/跑一次就停
  - 症状：某个任务没有周期执行
  - 证据动作：查任务栈水位（uxTaskGetStackHighWaterMark）；查任务里有没有阻塞点；查优先级抢占配置
  - 判定：栈溢出/饿死/优先级配置错
  - 对策：加大任务栈
  - 对策：任务循环加 vTaskDelay/队列阻塞
  - 对策：理清抢占与时间片
  - 依据：FreeRTOS 官方文档（uxTaskGetStackHighWaterMark / 栈溢出检查）
  - 转入：hardfault/stkerr
- **deadlock** 偶发死锁
  - 症状：系统跑一段时间卡死
  - 证据动作：查互斥锁获取顺序是否全局一致；查中断里是否误用非 FromISR API
  - 判定：锁排序/中断 API 误用
  - 对策：所有任务按同一顺序拿锁
  - 对策：开 configASSERT 抓现场
  - 对策：中断一律用 xxxFromISR 后缀 API
  - 依据：FreeRTOS 官方文档（FromISR API 语义）
- **prio-invert** 优先级反转
  - 症状：高优先级任务被低优先级任务长期阻塞
  - 证据动作：查资源保护用的是互斥量（带优先级继承）还是二值信号量
  - 判定：优先级反转
  - 对策：改用 xSemaphoreCreateMutex（继承机制）
  - 对策：缩小临界区范围
  - 依据：FreeRTOS 官方文档（互斥量优先级继承）
- **nvic-map** 中断优先级映射大坑
  - 症状：中断里调 RTOS API 就挂死
  - 证据动作：核对中断优先级数值与 configMAX_SYSCALL_INTERRUPT_PRIORITY；记住 Cortex-M 数值越大优先级越低（反直觉）
  - 判定：优先级映射错误
  - 对策：需要调 RTOS API 的中断：优先级数值必须 ≥ configMAX_SYSCALL...（即逻辑上不高于）
  - 对策：全工程统一 NVIC 分组并只初始化一次
  - 依据：FreeRTOS 官方文档（configMAX_SYSCALL_INTERRUPT_PRIORITY / 中断安全 API）
- **tick-dead** 任务卡在 vTaskDelay 不再继续
  - 症状：任务跑到第一个延时/队列等待就永远停住
  - 证据动作：查 SysTick 计数器是否在走；查 SysTick 优先级有没有被应用代码改掉；查有没有临界区把中断关了没恢复
  - 判定：时基没跑或被屏蔽
  - 对策：FreeRTOS 启动时自设 SysTick 优先级——应用别再动它
  - 对策：检查进/出临界区是否成对（PRIMASK/BASEPRI 恢复）
  - 依据：ARMv7-M Architecture Reference Manual (DDI 0403)
  - 转入：pwr/stop-clock

## boot — 启动失败

高频根因（按实战经验排序，非实测统计）：

1. HSE 起振失败（晶振焊接/负载电容）
2. 向量表偏移 VTOR 没设（Bootloader 跳 App）
3. 启动文件堆栈大小不足
4. BOOT0/BOOT1 引脚电平进了系统 Bootloader
5. 看门狗复位循环（IWDG 没喂）

- **clock-stuck** 卡在时钟初始化
  - 症状：上电后卡死在 SystemInit/HSE 等待循环
  - 证据动作：切 HSI 先跑起来；查晶振焊接与负载电容；查 PLL 倍频与 VOS 电压档位
  - 判定：晶振/PLL 配置问题
  - 对策：临时切 HSI 运行缩小范围
  - 对策：查 datasheet 的 VOS 档位与最高频率对应表
  - 依据：STM32 参考手册（如 RM0440，时钟/复位控制 RCC 章节）
- **vtor** Bootloader 跳 App 后异常
  - 症状：Bootloader 正常，跳转后 HardFault/不跑
  - 证据动作：查 App 里是否设置 VTOR；查向量表与链接脚本；查栈顶值（SP 初始化）
  - 判定：向量表/栈指针未重定位
  - 对策：跳转前关中断，App 开头 SCB->VTOR = FLASH_BASE | offset
  - 对策：确认 App 向量表第一项是栈顶地址、第二项是 Reset_Handler
  - 依据：ARMv7-M Architecture Reference Manual (DDI 0403)
  - 转入：hardfault/iaccvio
- **reset-source** 复位原因判定
  - 症状：设备周期性复位/复位原因不明
  - 证据动作：读 RCC->CSR（或同系列复位标志寄存器）分清：IWDG/WWDG/软复位/上电/引脚复位
  - 判定：看门狗循环或电源问题
  - 对策：IWDG 复位→查喂狗路径（哪个任务喂、卡在哪没喂到）
  - 对策：引脚复位→查 NRST 电路与干扰
  - 依据：STM32 参考手册（如 RM0440，时钟/复位控制 RCC 章节）
  - 转入：pwr/wakeup-src
- **boot-pins** BOOT 引脚状态
  - 症状：App 不跑但 SWD 能连
  - 证据动作：查 BOOT0/BOOT1 电平；读 DBGMCU 确认 CPU 在哪个区执行
  - 判定：从系统 Bootloader 启动了
  - 对策：BOOT0 拉低（GND）后复位
  - 对策：检查 BOOT 引脚的外围电路
- **swd-locked** SWD 连不上（看似起不来）
  - 症状：以为程序没跑，但上电电流正常；SWD 偶尔能连
  - 证据动作：查 PA13/PA14（SWDIO/SWCLK）是否被初始化代码配走；查是否进了低功耗（SWD 断连）；用 Connect under Reset 试
  - 判定：调试口被软件抢走或低功耗断连
  - 对策：初始化代码保留 SWD 引脚复用
  - 对策：Connect under Reset（拉低 NRST 时连接）
  - 对策：调试期低功耗要开 DBGMCU 的 DBG_STOP/DBG_STANDBY 保持调试连接
  - 依据：STM32 参考手册（如 RM0440，低功耗章节）

## can — CAN / CAN-FD 通信不通

高频根因（按实战经验排序，非实测统计）：

1. 物理层故障（终端电阻/收发器供电/显性电平不对，最多见）
2. 位时序不匹配（波特率/采样点不一致，偶发不定时错帧）
3. GPIO 复用模式与 CAN 外设时钟未配对使能
4. CAN 过滤器配置错误（把帧全滤掉，收不到）
5. 发送邮箱满/未清、发送失败后未复位邮箱导致发不出去

- **can-phy** 物理层先量（示波器）
  - 症状：CAN_H/CAN_L 差分电平异常或无波形，完全收不到也不发
  - 证据动作：用示波器量显性/隐性电平下 CAN_H/CAN_L 差动电压；核对总线两端是否各有一个 120Ω 终端电阻；确认收发器供电与 STB/standby 待机脚电平
  - 判定：物理层故障（电平/终端/收发器供电）
  - 对策：在总线两端各接一个 120Ω 终端电阻（中间节点不加）
  - 对策：核对收发器供电与待机脚 STB 电平（STB 应为正常工作态）
  - 对策：排查收发器虚焊/接反/CAN_H 与 CAN_L 接错
  - 对策：用示波器确认显性差动电平约 2V
  - 依据：ISO 11898-1:2015；ISO 11898-2:2016
- **can-bit** 位时序与采样点
  - 症状：低速偶发错误帧、越远越长线越出错，或两端速率不一致直接不通
  - 证据动作：核对双方位速率（仲裁段/数据段）一致；回读位时序寄存器确认采样点；CAN-FD 需分别核对仲裁段与数据段采样点
  - 判定：位时序不匹配（波特率/采样点）
  - 对策：把仲裁段采样点配到 75%–87.5%
  - 对策：CAN-FD：数据段按更高速率单独配采样点，保证双方一致
  - 对策：两端用同一参考源（外部晶振）并核对 SJW 取 1–4
  - 依据：ISO 11898-1:2015；STM32 参考手册（如 RM0440/RM0090，FDCAN/ bxCAN 位时序寄存器章节）
- **can-filter** 过滤器从全收开始
  - 症状：能发能收但就是收不到目标 ID 报文，HAL 收到满却匹配不上
  - 证据动作：先把过滤器掩码配全 0（全收）验证链路通；确认过滤器初始化与信道初始化顺序一致；核对过滤的 mask/id 掩码位方向
  - 判定：过滤器配置把目标帧滤掉了
  - 对策：调试期用掩码全 0（接收所有 ID）先验证链路，再逐步收紧到目标 mask+id
  - 对策：核对过滤器初始化与信道初始化的先后顺序（不同库口径）
  - 对策：核对 RTR/扩展帧标准帧位与 mask 位数对应关系
  - 依据：STM32 参考手册（如 RM0440/RM0090，FDCAN/ bxCAN 过滤器章节）
- **can-tx** 发不出去
  - 症状：应用调发送返回忙/超时，或只发一次就再也不发；对方始终收不到
  - 证据动作：回读发送邮箱状态寄存器（该系列手册口径）确认邮箱满/空；发送失败后检查错误计数是否累积、邮箱是否仍占用；定位是否只发送了首帧
  - 判定：发送邮箱满/未清或发送失败未复位
  - 对策：等到有空邮箱（空闲位）再放新报文，失败后按手册清发送优先级/复位邮箱
  - 对策：避免只发一次就死：发送完成标志未清或邮箱优先级配置导致后续排队阻塞
  - 对策：确认发送完成中断或轮询等待逻辑无初始化漏洞
  - 依据：STM32 参考手册（如 RM0440/RM0090，FDCAN/ bxCAN 发送邮箱与发送优先级章节）
- **can-busoff** 错误帧与 bus-off
  - 症状：一直插入错误帧，累计后进 bus-off 收也收不到，改错误计数又复现
  - 证据动作：回读错误计数寄存器初步定位错误类型（该系列手册口径）；回读协议信号位区分位错误/位填充/形式错误；bus-off 后按手册确认自动还是手动重进入初始化
  - 判定：错误计数器超阈值/bus-off
  - 对策：读 TEC/REC 错误计数：TEC 高侧重发送侧错误，REC 高侧重接收干扰
  - 对策：bus-off 后按手册的自动恢复或触发重进入初始化的流程，不要跳过
  - 对策：排查总线短路/端子/星型拓扑与阻抗不匹配等诱因
  - 依据：ISO 11898-1:2015；STM32 参考手册（如 RM0440/RM0090，FDCAN/ bxCAN 错误计数与中断状态章节）

## pwr — 低功耗与唤醒异常

高频根因（按实战经验排序，非实测统计）：

1. 唤醒后系统时钟没重配（外设全乱了：乱码/定时不准）
2. 唤醒源没配对或唤醒标志没清（睡死叫不醒）
3. 有中断标志没清干净——刚进停机立刻被唤醒，量不到低电流
4. 调试器连接改变低功耗行为（DBGMCU）

- **stop-clock** 唤醒后外设乱码/定时不准
  - 症状：停机模式唤醒后 UART 乱码、定时器变慢
  - 证据动作：读回 RCC 时钟状态寄存器：唤醒后系统时钟常回落到 HSI/MSI（PLL 已关）
  - 判定：唤醒后时钟未重配
  - 对策：唤醒后第一时间重跑时钟初始化（重启 PLL 并切换）
  - 对策：或外设时钟源改用唤醒后仍可用的源，并重算波特率/分频
  - 依据：STM32 参考手册（如 RM0440，低功耗章节）
- **wakeup-src** 睡死叫不醒
  - 症状：进入停机/待机后唤醒不了
  - 证据动作：逐项核对唤醒源：EXTI 线与边沿、RTC 闹钟/唤醒定时器；查唤醒标志（WUF 等）是否在进睡前清掉
  - 判定：唤醒源配置/标志未清
  - 对策：进睡前先清唤醒标志，再使能唤醒源，最后进低功耗
  - 对策：待机模式的唤醒源只有少数特定引脚/RTC——查手册的唤醒源表，别按停机模式的经验配
  - 依据：STM32 参考手册（如 RM0440，低功耗章节）
- **sleep-not-enter** 进不了低功耗（电流降不下来）
  - 症状：调了 WFI 但整板电流没变
  - 证据动作：查未清的外设中断标志（一进停机立刻被唤醒）；查外设时钟是否全关、引脚是否悬空漏电
  - 判定：标志未清/外设未关
  - 对策：进睡前清干净全部外设标志、关闭不用的外设时钟
  - 对策：配 GPIO 为模拟输入防悬空漏电；量电流波形找唤醒瞬间
  - 依据：STM32 参考手册（如 RM0440，低功耗章节）
  - 转入：rtos/tick-dead
- **dbg-block** 调试器挂着正常，拔了就异常
  - 症状：联调时低功耗/时序行为与脱机不一致
  - 证据动作：查 DBGMCU 的 DBG_STOP/DBG_STANDBY（调试期冻结低功耗）；排查是否依赖了调试器在场的时序
  - 判定：调试器改变时序/低功耗行为
  - 对策：需要脱机复现时关掉调试冻结位，或改用故障快照/串口打印
  - 对策：时序敏感逻辑不依赖调试期时序
  - 依据：STM32 参考手册（如 RM0440，低功耗章节）
  - 转入：boot/swd-locked

## usb — USB 枚举失败 / CDC 不通

高频根因（按实战经验排序，非实测统计）：

1. 48MHz 时钟未就绪或不精确（HSI48 未校准/CRS 未跑/PLL 分频错），枚举直接失败
2. DP 上拉使能/软断开位配置错，主机始终识别不到设备
3. 端点 0 的 GET_DESCRIPTOR 响应错误（描述符长度/字符串/地址设置时序），枚举卡在某一步
4. PMA/端点缓冲大小与对齐错（double-buffer/对齐），传输错乱丢数据
5. CDC 在主机侧无驱动/INF 不对，设备管理器识别不出虚拟串口

- **usb-clock** 先验证 48MHz 时钟
  - 症状：枚举完全失败，主机不识别或不稳定
  - 证据动作：读 USB 时钟源状态：确认 48MHz 就绪且精度达标；HSI48 要校准（CRS 对 USB SOF 校准）或用 PLL 精确分频；示波器看 D+/D- 有无活动确认时钟域在跑
  - 判定：USB 时钟未就绪或不精确
  - 对策：HSI48 开 CRS 校准（对 USB SOF 同步）
  - 对策：或用 PLL 精确倍分频出 48MHz
  - 对策：时钟错枚举必败，先排除时钟再查别的
  - 依据：USB 2.0 规范（枚举流程）；STM32 参考手册（如 RM0440，USB 章节）
- **usb-phy** DP 上拉与软断开
  - 症状：插上没反应，主机不弹设备也不识别；换线/换口都一样
  - 证据动作：核对 DP 上拉使能位与软断开位：重枚举要先断开再连接；示波器量 D+/D- 静止电平确认上拉是否生效
  - 判定：上拉/软断开没配对或断连序列错
  - 对策：复位后等主机检测到上拉再响应后续传输
  - 对策：重枚举流程：先断开/去连接→延时→再连接，别在同一次枚举里反复切换
  - 依据：USB 2.0 规范（枚举流程）；STM32 参考手册（如 RM0440，USB 章节）
- **usb-enum** 端点 0 与描述符
  - 症状：枚举卡在某一步（卡 SET_ADDRESS 或描述符请求后不继续）；设备管理器报错 43
  - 证据动作：抓 USB 总线（USB 分析仪/逻辑分析仪）看 GET_DESCRIPTOR 包是否被正确应答；核对描述符长度、字符串索引、地址设置后的时序（SET_ADDRESS 后需延时再响应）
  - 判定：端点 0 描述符/地址时序处理错
  - 对策：设备描述符固定 18 字节；配置描述符核对 wTotalLength 与实际返回字节数一致（含接口/端点子描述符，长度不符主机会中止配置）
  - 对策：SET_ADDRESS 后延时约 2ms 再收下一个包（经验值；别在改地址前回带新地址的描述符请求）
  - 对策：字符串描述符索引与语言 ID 配对无误
  - 依据：USB 2.0 规范（枚举流程）；STM32 参考手册（如 RM0440，USB 章节）
  - 转入：usb-clock
- **usb-buffer** 缓冲与对齐
  - 症状：传输偶发错乱/丢字节；双缓冲时数据互相覆盖
  - 证据动作：核对每个端点的缓冲描述符/PMA：偏移与大小、对齐（手册要求的对齐规则）是否一致；double-buffer 两段基址与大小是否配对且与描述符区不重叠
  - 判定：端点缓冲大小/对齐/double-buffer 配置错
  - 对策：按手册对齐规则给缓冲基址，避免缓冲与描述符区重叠
  - 对策：double-buffer 两段基址与大小逐一核对口径一致
  - 依据：STM32 参考手册（如 RM0440，USB 章节）
- **usb-cdc** CDC 驱动与主机识别
  - 症状：枚举成功但设备管理器里没有虚拟串口，或不识别成 CDC
  - 证据动作：设备管理器看枚举到哪一层：是'未知设备/错误 43'、虚拟串口在但打不开；核对 CDC 描述符组合（IAD/接口/端点），换主机与标准驱动复现排除驱动/INF 问题
  - 判定：CDC 类描述符/主机驱动问题
  - 对策：核对 CDC 描述符表：接口与端点方向/数量匹配
  - 对策：换主机或装标准 CDC 驱动复现，排除本地驱动与 INF 因素
  - 依据：USB 2.0 规范（枚举流程）；STM32 参考手册（如 RM0440，USB 章节）
  - 转入：comm/layer1-config

## flash — 片内 Flash 编程/擦除异常

高频根因（按实战经验排序，非实测统计）：

1. 解锁命令没做全（解锁密钥寄存器顺序错），编程/擦除操作位根本没进去
2. 编程/擦除操作位顺序错或没设，写了不生效
3. 忙标志没轮询就做下一步，Flash 还在忙（擦除毫秒级）
4. 写粒度/对齐不符或 ECC 型读改写把相邻字节写坏
5. 写 Flash 时中断向量取指 stall；或选项字节读保护开了连不上/读不出

- **fl-unlock** 解锁与命令序列
  - 症状：写/擦 Flash 没反应，状态寄存器报操作错，或写了重启后不生效
  - 证据动作：回读状态寄存器：先核对解锁密钥寄存器是否已按顺序写入；再核对编程/页擦/扇区擦操作位在启动操作前是否按参考手册顺序设置
  - 判定：解锁没做全或命令序列顺序错
  - 对策：严格按参考手册顺序：先解锁密钥寄存器、置操作位、写数据/启动命令，最后才轮询等待
  - 对策：写了没生效：回读操作位确认命令已锁存，别跳过操作位直接写
  - 依据：STM32 参考手册（如 RM0440，片内闪存章节）
- **fl-wait** 等待与超时
  - 症状：写后立即读回旧数据或偶发写坏；在中断里做擦除长时间卡死/看门狗复位
  - 证据动作：查忙标志是否在擦/写后轮询过（页擦除毫秒级、整片数秒级）；核对超时与看门狗窗口；检查 ISR 里是否做了擦除
  - 判定：忙标志未轮询/超时不够/ISR 里做擦除
  - 对策：擦/写完成后才读回校验，别抢时间
  - 对策：不要在 ISR 里做重擦除操作，移到主上下文或后台任务处理
  - 依据：STM32 参考手册（如 RM0440，片内闪存章节）
- **fl-align** 写粒度与对齐
  - 症状：写小缓存（1 字节/奇数长度）报错或数据被覆盖；ECC 型 Flash 读改写把相邻字节写坏
  - 证据动作：看参考手册的编程最小粒度（半字/双字等按手册口径）；回读编程长度/地址配置；ECC 型则检查目标地址对齐与整字重编程
  - 判定：写粒度/对齐不符
  - 对策：按手册对齐到最小编程单元再整单元写入
  - 对策：ECC 型 Flash 做读-改-写整字并保证地址对齐
  - 依据：STM32 参考手册（如 RM0440，片内闪存章节）
- **fl-stall** 写 Flash 时程序卡死
  - 症状：写/擦 Flash 期间中断响应明显变慢或程序看去卡死
  - 证据动作：量度中断延迟：写 Flash 期间 CPU 从片内 Flash 取指会 stall；查中断向量与关键处理是否仍驻留 Flash
  - 判定：Flash 忙时取指/中断被延迟
  - 对策：把关键中断向量与处理搬到 RAM 执行（特定系列支持）
  - 对策：或把非紧急写擦推迟到低优先级，避免与高实时中断冲突
  - 依据：STM32 参考手册（如 RM0440，片内闪存章节）
- **fl-option** 选项字节与保护
  - 症状：配了读保护后 SWD 连不上/读不出 Flash；改选项字节后不生效
  - 证据动作：读选项字节寄存器核对读保护/写保护配置；改完后按手册重载选项字节并复位验证
  - 判定：选项字节读保护开启或未重载
  - 对策：开发期先不开读保护（用最低档），需要时再加回
  - 对策：改选项字节后按手册重载或复位才生效
  - 对策：确认写保护选项没有阻断烧写
  - 依据：STM32 参考手册（如 RM0440，片内闪存章节）

## rtc — RTC 走不准 / 备份域丢配置

高频根因（按实战经验排序，非实测统计）：

1. 备份域写保护链条没走完（备份域写使能位→写保护解锁→进入初始化模式），写入根本没生效
2. 每次上电都重写时间/日期，没判备份域复位标志，把首次初始化当成了每次都要跑
3. LSE 起振慢/失败，时钟源质量差或退化导致走时误差
4. 读日历前没做数据同步握手（RSF），读到半更新态错误值
5. 唤醒定时器只写了低位/中断标志没清，周期与唤醒时机不对

- **rtc-domain** 备份域与写保护链
  - 症状：改 RTC 配置/备份寄存器明明执行了却不生效，掉电重来还是旧值
  - 证据动作：核对是否先开备份域写使能位，再写对写保护位解锁序列，最后在进入 RTC 初始化模式后再写入；每步回读确认
  - 判定：写保护/初始化模式链路没走完，写入无效
  - 对策：先使备份域写使能位，再按手册写对写保护解锁口令，最后进入初始化模式后再改寄存器
  - 对策：每步写后回读验证，别依赖一次寄存器写入就成功
  - 依据：STM32 参考手册（如 RM0440，RTC 章节）
- **rtc-first** 上电首次初始化
  - 症状：每次上电时间都回到出厂值，或老被重置
  - 证据动作：读备份域复位标志判定是首次上电还是热复位；首次才走完整初始化，否则直接读取保留已有时间
  - 判定：没判首次上电标志，把初始化当每次都要跑
  - 对策：用备份域复位标志判断是否需要初始化，首次才写时间/日期，热复位直接读取
  - 对策：初始化期间按序关闭再重新使能写保护，完成后回读校验
  - 依据：STM32 参考手册（如 RM0440，RTC 章节）
- **rtc-lse** LSE 起振与时钟兜底
  - 症状：走时偏快/偏慢或时好时坏，低温/上电时尤其明显
  - 证据动作：读 LSE 起振就绪标志，起振通常要几百毫秒到几秒；条件允许用示波器量 32.768k 引脚
  - 判定：LSE 起振慢/失败，时钟源质量差或退化
  - 对策：等 LSE 就绪标志置位后再配 RTC 时钟源，别直接切过去
  - 对策：起振失败时兜底切到 LSI 并置错误标记（精度会下降）
  - 对策：用 MCO/旁路输出验证外部晶振是否真在工作
  - 依据：STM32 参考手册（如 RM0440，RTC 章节）
  - 转入：boot/clock-stuck
- **rtc-sync** 日历同步
  - 症状：读时间有时对有时不对，或读数会跳变
  - 证据动作：读日历前先等数据同步标志就绪或加同步锁；连续读两次校验一致性
  - 判定：未做数据同步握手，读到半更新态数据
  - 对策：读日历前查询数据同步标志就绪后再读
  - 对策：或二进制连续读两次一致才采用，避免寄存器半更新
  - 依据：STM32 参考手册（如 RM0440，RTC 章节）
- **rtc-wake** 唤醒定时器
  - 症状：RTC 唤醒没到点就醒或到点不醒，闹钟周期不对
  - 证据动作：核对 16 位计数值加高位扩展位组成的完整周期；查唤醒中断标志是否在进唤醒前清掉
  - 判定：唤醒定时器高低位口径/中断标志未清
  - 对策：唤醒定时器按 16 位+扩展位拼成完整周期，别只写低位
  - 对策：进低功耗前清唤醒标志再使能，唤醒后再次确认标志已清
  - 依据：STM32 参考手册（如 RM0440，RTC 章节）

## display — 显示黑屏 / 花屏 / 触摸异常

高频根因（按实战经验排序，非实测统计）：

1. 背光亮不等于屏在工作——全白说明初始化没进/没刷显存，全黑要先查背光
2. 复位与上电序列不对（复位脉宽/延迟不足、SLEEP OUT 后没等就绪）
3. 接口时序不匹配（8080 写时序/SPI 相位/RGB 的 DE-HSYNC-VSYNC 极性与像素时钟）
4. 帧缓冲格式或字节序错导致花屏，刷新无 TE 同步/无双缓冲导致撕裂
5. 触摸 I2C 地址/中断脚/坐标方向与分辨率换算未对上

- **disp-backlight** 背光先确认
  - 症状：屏幕全黑或全白没画面，先分清背光状态
  - 证据动作：先看背光亮不亮；全白=面板在刷纯白而背光亮，说明初始化没进或没刷显存；全黑再查背光使能与 PWM
  - 判定：全白=初始化没进；全黑先查背光
  - 对策：先确认背光电源、使能脚与 PWM 占空比
  - 对策：全白时查控制器初始化码与 SLEEP OUT/显示开命令是否执行
  - 依据：LCD 控制器数据手册
- **disp-reset** 复位与上电序列
  - 症状：上电后花屏/无响应，偶发不亮
  - 证据动作：量复位脚脉宽与复位后到发指令的延时；逐条核对初始化码是否全部下发且无出错
  - 判定：复位时序/初始化码未按数据手册走
  - 对策：复位脚脉宽满足数据手册最小要求，复位后等足延迟再发命令
  - 对策：SLEEP OUT 后必须等待面板就绪延迟
  - 对策：逐条比对初始化码，错发一条屏就异常
  - 依据：对应显示控制器数据手册（初始化/时序章节）
- **disp-iface** 接口时序
  - 症状：有信号但画面错乱/雪花/颜色发怪
  - 证据动作：量 8080 写时序或 SPI 时钟相位；RGB 查 DE-HSYNC-VSYNC 极性与像素时钟频率是否在面板容差内
  - 判定：接口时序/极性与像素时钟不匹配
  - 对策：8080 波形检查建立/保持时间，SPI 核对相位与速率上限
  - 对策：RGB 接口按数据手册核对 DE/HSYNC/VSYNC 极性、行场消隐与像素时钟
  - 依据：对应显示控制器数据手册（初始化/时序章节）
  - 转入：comm/layer2-timing
- **disp-tear** 花屏与撕裂
  - 症状：画面局部错乱，或刷新时上下撕裂
  - 证据动作：核对帧缓冲格式（RGB565/888、字节序）、行宽对齐与起始地址；有 TE 同步引脚则用 TE 握手+双缓冲
  - 判定：帧缓冲格式/字节序错，或撕裂同步缺失
  - 对策：帧数据格式与面板一致（RGB 顺序、字节序），行首地址按面板要求对齐
  - 对策：开 TE 同步或改用双缓冲，等 TE 后再刷新帧避免撕裂
  - 依据：对应显示控制器数据手册（初始化/时序章节）
- **disp-touch** 触摸异常
  - 症状：能显示但触摸没反应，或坐标反/偏、触点对不上位置
  - 证据动作：核对 I2C 地址/中断引脚/复位配置，量中断是否有边沿；点几个角落量坐标，核对方向与分辨率换算
  - 判定：触摸地址/中断/坐标映射未对上
  - 对策：核对 I2C 地址与中断脚，量中断边沿确认数据上来了
  - 对策：按实际张贴方向做坐标旋转/镜像，再做分辨率线性换算
  - 依据：对应显示控制器数据手册（初始化/时序章节）
  - 转入：comm/layer2-timing

## fpga-rtl — FPGA/RTL 排障（综合后行为异常/资源/工具链）

高频根因（按实战经验排序，非实测统计）：

1. parameter/端口漏透传到全部例化点——静默取默认或只报警告、位流照常生成（最高频）
2. 存储阵列加复位循环杀死 RAM 推断，退化成 N×W 个触发器（不报任何警告）
3. 跨时钟域违例：多 bit 直接同步、无格雷码指针、复位未同步释放
4. I2C 主控把从机时钟拉伸误判为本地超时（等电平与拉伸是同一观测）
5. 实验脚手架/诊断探针长期留在生产路径上，'过于整齐'的异常其实是配置
6. 仿真器静默假信息（格式化输出串分支、$fatal 不置退出码）误导判决
7. 误判工具/流程信号：进程在≠编译在跑（看 CPU 时间），读数 0≠链路断（先交叉验证量具）

- **silent-default** 帧流/位流正常但某功能全零或恒定 —— 先查漏透传
  - 症状：综合 0 ERROR、功能自测 PASS，但某个值恒 0/恒全 F/恒不动；或'帧流正常但 payload 全 0'
  - 证据动作：grep 新改 parameter/端口的模块名 → 逐个例化点核对透传（含中间封装层，每层都要过）；再看构建日志里的端口/参数告警逐条读
  - 判定：parameter 漏接=完全不报（静默取默认，同 C 未初始化变量）；port 漏接=只报警告、照样出位流
  - 对策：默认值按频率/场景自动推导（parameter integer P = (F>=300000) ? 1 : 0），让'漏接'的兜底行为仍是对的
  - 对策：定位三步：git log 锁上一个好版本 → git diff 好坏版本找行为变更 → grep 例化点核对透传
  - 对策：A/B 位流对照（同下载路径、唯一变量=位流）是最终判据，别用推理代替实测
  - 依据：IEEE 1364-2005 Verilog LRM（parameter 与端口连接语义）；Gowin 综合用户指南（Synthesis User Guide）
- **ram-inferr** 资源压不下去 —— 复位循环杀 RAM 推断 / 先算资源账
  - 症状：把存储改成数组想省 REG，综合后 REG 没明显下降、SSRAM/BSRAM 计数没涨（或为 0）；或砍 REG 几乎不降 CLS
  - 证据动作：先查存储数组有没有复位循环（for mem[i] <= 0）——有则综合器放弃 RAM 推断，退化成 N×W 个触发器且不报错；再读综合报告的 LUT/REG/CLS 占比，确认资源账由谁主导
  - 判定：门禁若是 CLS，先看它由 LUT 还是 REG 主导：SSRAM/BSRAM 不涨说明推断没成功；砍非主导项收益极低
  - 对策：存储数组：无复位循环、无 integer reset_index；上电初值靠配置期初值；'哪些通道有效'用独立位图（channel_valid），不靠读数判 0
  - 对策：推断成功的标志：REG 数量下降 + SSRAM/BSRAM 计数上升（具体数值以综合报告为准）；不涨就是没推断成功
  - 对策：小型'宽×深'存储优先分布式 RAM（LUTRAM）：异步读无需地址对齐计数器，比显式 BSRAM 原语（同步读）简单
  - 对策：网表归因别猜：.vg 网表按外层 module 分桶统计 LUT/FF 得每路成本，再按驱动网名找单项大户
  - 对策：'宽扁平总线夹在两棵 mux 树之间'是常见资源黑洞——数据改按地址访问，mux 树整棵消失
  - 依据：Gowin 综合用户指南（Synthesis User Guide）；AMD/Xilinx UG901 Vivado Synthesis（RAM 推断编码风格）
- **cdc** 跨时钟域（CDC）——偶发数据撕裂/亚稳态/复位异常
  - 症状：偶发数据错位、概率性异常、复位后部分逻辑状态不对、综合器 CDC 报告有违例
  - 证据动作：按数据宽度分类：单 bit 控制信号→两级触发器同步器；快→慢域打拍+边沿检测；多 bit 总线→禁止直接同步，用握手(req/ack)或异步 FIFO；计数器跨域→格雷码；复位→每域独立异步复位、同步释放
  - 判定：多 bit 直接同步必偶发撕裂；计数器跨域非格雷码必读脏值；门控时钟/行波计数器是 CDC 工具必查项
  - 对策：用综合工具 CDC 报告兜底（Vivado report_cdc / Gowin 时序报告的跨域路径）
  - 对策：异步 FIFO 指针必须格雷码（相邻只变 1 位），空/满判定用同步后的指针
  - 对策：异步 FIFO 深度按写入/读出速率与突发长度核算，避免上溢/下溢（可用 embedded-timing-calc fpga-fifo 校验）
  - 依据：Cummings, Clock Domain Crossing (CDC) Design & Verification Techniques Using SystemVerilog（SNUG 2008）；Cummings, Simulation and Synthesis Techniques for Asynchronous FIFO Design（SNUG 2002）；Gowin 时序分析用户指南（Timing Analysis User Guide）
- **i2c-stretch** I2C 主控偶发整路冻结 —— 时钟拉伸被本地超时误杀
  - 症状：事务随机中止、host 失步、整路永久停摆；日志里 timeout_error 频发；且'等 SCL 变高'的等待窗口远小于从机实际拉伸时长
  - 证据动作：先确认：master 观测到 scl_in 为低时无法区分①总线 RC 爬升（百 ns 级）还是②从机时钟拉伸（可达毫秒级）——任何'爬升兜底'短超时都会把正常拉伸判成超时
  - 判定：'等电平'与'等拉伸'落在同一观测上，本地短超时必然误杀；等待必须统一交给按拉伸量级设计的 stretch 检测器
  - 对策：新增任何'等待电平/事件'状态前先问：这个等待会不会与从机时钟拉伸落在同一观测上？是则复用 stretch 检测器，禁止另设短超时
  - 对策：仿真必须覆盖拉伸档位：从 0 到百 µs 级扫描，'拉伸下 timeout_error 恒 0'是验收条件——光测正常时序不算过
  - 对策：I2C 规范要求主控支持时钟拉伸：支持拉伸=允许等待（超时策略统一兜底）
  - 对策：历史'某频率失败'的记录先存疑：可能是把'短超时<从机拉伸'误归因为'频率不可行'
  - 依据：NXP UM10204 I2C-bus specification and user manual（clock stretching）；BNO08X datasheet（clock stretching 要求）
- **nba-oldval** RTL 仿真行为诡异 —— 非阻塞赋值同拍读旧值 / 仿真器静默假信息
  - 症状：同拍内先赋值后使用读到旧值（NBA 语义）；仿真报告一行里同时出现 PASS 和 FAIL 字样；$fatal 后退出码仍是 0
  - 证据动作：NBA（<=）同拍读旧值是 Verilog 语义——把'本拍应读到新值'的逻辑拆到下一拍或改阻塞赋值（仅限组合 always）；仿真报告判据只认数字行
  - 判定：iverilog 四坑：%s+三目会同时打出两分支文本（改 if/else）；$fatal 不置非零退出码（判决只读报告正文）；sticky 标志修复前后同值不配当判据；判读历史报告以数字为准忽略判定文字
  - 对策：凡 %s 参数是三目，一律改 if/else 分条打印
  - 对策：做变异体对照前先问：这个量在两版下真会不同吗？不同才配当判据
  - 对策：仿真定向复现'坏行为'再改——改完必须复现消失，不能只靠上板
  - 依据：IEEE 1364-2005 Verilog LRM（非阻塞赋值与仿真调度语义）；IEEE 1800-2017 SystemVerilog LRM（$fatal 与仿真退出语义）
- **measure-vs-fault** 实测数值'过于整齐'或量具读零 —— 先查配置与量具，再怀疑缺陷
  - 症状：某几路严格恒定同一数值/同一周期（过于整齐）；或诊断探针读恒 0/恒全 F；或串口读 0 字节
  - 证据动作：两步走：①'过于整齐'（严格整周期、多路相等）= 被配置成周期任务的指纹 → grep 该路 localparam/分频/周期配置（实验脚手架/诊断探针类命名默认是待撤项）；②读数恒 0 → 第一嫌疑是量具没接上（串口监听工具不可信，用独立串口库或逻辑分析仪交叉验证）
  - 判定：'过于整齐'先找配置，'过于随机'（换路/时长不定）才查缺陷；量具与被测对象必须分开怀疑——先证量具干净
  - 对策：实验脚手架/诊断探针默认待撤，撤时一次只撤一个维度
  - 对策：诊断实验设计成'配对独特值'：激励值互不相同且不与自然结果重合，让两个假设给出可区分的读数（配对量同结构互为对照组）
  - 对策：串口/量具读 0 先用另一条独立通路交叉验证，再改 RTL/下结论
  - 对策：后台编译完成与否看构建日志的时间戳与内容，不看进程是否存在；进程忙闲看 CPU 时间（长时间低 CPU 占用=空转）
  - 依据：Gowin 云源软件用户指南（Cloud Source User Guide）；IEEE 1364-2005 Verilog LRM（仿真输出与系统任务语义）
- **regression-attrib** 改完 RTL 某路异常 —— 嫌疑排序：先查自己再查硬件
  - 症状：改动+重综合+重下载后某路没数据/冻结；但改动前该路正常，物理连线没动
  - 证据动作：按嫌疑度排序逐项自查：①回烧改前位流对照（恢复=改动引入，查 diff）②PnR 布局漂移/拥塞③下载部分失败（重下排除）④上电时序⑤全排除才查物理接线
  - 判定：凡'之前好好的、我改完才坏'，一律先写'未定位，疑改动回归'再自查——物理嫌疑排最后，需回烧对照+物理复测双证据才有资格落'硬件问题'
  - 对策：保留上一个好版本位流与备份路径，A/B 对照是定位利器
  - 对策：每次重综合布局会漂移——'布通过'不代表'每次都布通过'，资源/时序余量要留（如 CLS ≤95%）
  - 对策：时序报告 WNS/TNS 为负时先降频或砍组合逻辑深度，别靠反复重综合碰运气
  - 对策：注意板级事实的分清：'暂时缺'与'设计上就没有'不同——后者不进缺口清单
  - 依据：Gowin 时序分析用户指南（Timing Analysis User Guide）；Gowin 综合用户指南（Synthesis User Guide）
